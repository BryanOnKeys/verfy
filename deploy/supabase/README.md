# Deploy: Supabase

Atls Team stores everything in one Supabase project: Postgres (tables, RLS, functions), Auth (users and sessions) and Storage (the private `exports` bucket). Do this **before** Vercel, because Vercel needs the project's URL and keys.

## Files used

| File | What it is |
| --- | --- |
| `supabase/migrations/20261011000100_atls_schema.sql` | Tables, constraints, indexes, RLS policies, role-checking functions, audit hash chain |
| `supabase/migrations/20261011000200_storage_exports.sql` | Private `exports` bucket (no client storage policies) |
| `supabase/migrations/20261011000300_advisories_initial.sql` | Public, sourced Atls Advisories (generated by `scripts/advisories.mjs`) |
| `supabase/migrations/20261012000100_hardening.sql` | Statement timeouts for `anon` / `authenticated`, self-pruning rate-limit windows |
| `supabase/migrations/20261012000200_mfa.sql` | Two-factor authentication enforced in RLS: with a verified factor, an aal1 session sees no organization data |
| `supabase/seed.sql` | **Local development only** (DEMO org, test-key receipts). Never run it in production. |
| `supabase/config.toml` | Supabase CLI settings for local development |
| `supabase/tests/*.test.ts` | RLS / tenant-isolation tests (run with `npm test`, on PGlite) |

## 1. Create the project

1. Sign in at <https://supabase.com/dashboard> and create a project. Pick the region closest to your users (it cannot be changed later). Save the database password in your password manager.
2. **Project Settings → API Keys**: create (or copy) a **publishable key** (`sb_publishable_…`) and a **secret key** (`sb_secret_…`).
   - Older projects that only have `anon` and `service_role` keys work too: use `anon` as the publishable key and `service_role` as the secret key. Supabase is retiring the legacy keys, so prefer the new ones.
   - The secret key bypasses RLS. It goes only into Vercel's server environment, never into code, chat, screenshots or the browser.

## 2. Apply the migrations

Install the Supabase CLI (<https://supabase.com/docs/guides/local-development/cli/getting-started>), then from the repository root:

```bash
supabase login
supabase link --project-ref <your-project-ref>     # the ref is in the project URL
supabase migration list                             # see what will be applied
supabase db push                                    # applies supabase/migrations/* in order
```

`supabase db push` only applies migrations that have not run yet. **Never run `supabase db reset` against production**: it drops all data. Do not run `seed.sql` in production.

Check: in **Table Editor** you should see `orgs`, `receipts`, `policies`, `locks`, `audit_log`, … and in **Storage** a private bucket named `exports`. In **Table Editor → advisories** there are 4 published rows.

## 3. Configure Auth

**Authentication → URL Configuration**

- **Site URL**: your production URL, e.g. `https://atls.example.com`
- **Redirect URLs** (add each):
  - `https://atls.example.com/auth/callback`
  - `https://atls.example.com/auth/confirm`
  - for Vercel previews, if you want sign-in there: `https://*-<your-team>.vercel.app/auth/callback`

**Authentication → Providers → Email**

- Keep **Confirm email** on.
- Set the OTP / magic-link expiry to 3600 seconds or less.
- Minimum password length: 12 (Atls also enforces 12).

**Authentication → SMTP**: configure your own SMTP provider. The built-in sender is rate limited and meant for testing.

**Authentication → Multi-Factor**

- Keep **TOTP (App Authenticator)** enabled (it is on by default). Users turn on two-factor authentication under Settings in the Atls dashboard; the database then refuses their organization data until the code step is done.

**Authentication → Attack Protection** (Bot and Abuse Protection)

- **CAPTCHA (recommended for public sign-up)**: create a Turnstile widget in the Cloudflare dashboard for your domain. Put its **secret key** here (provider: Turnstile) and its **site key** in Vercel as `NEXT_PUBLIC_TURNSTILE_SITE_KEY`. Enable both together: with only the Vercel side, forms show the widget but Supabase does not check it; with only the Supabase side, every sign-in fails.
- **Prevent use of leaked passwords**: turn on if your plan offers it.
- **Rate limits**: keep Supabase's own email and sign-in limits; Atls adds per-IP, per-account and per-recipient limits on top.

**GitHub sign-in (optional)**

1. GitHub → Settings → Developer settings → OAuth Apps → New. Callback URL: `https://<your-project-ref>.supabase.co/auth/v1/callback`.
2. Supabase → Authentication → Providers → GitHub: paste the client ID and secret there (not in Vercel).
3. In Vercel set `NEXT_PUBLIC_AUTH_GITHUB_ENABLED=true` and redeploy. Leave it `false` until the provider works.

## 4. Production hardening (Supabase dashboard)

From Supabase's production checklist (<https://supabase.com/docs/guides/deployment/going-into-prod>):

- [ ] **Database → Settings → SSL**: enforce SSL connections.
- [ ] **Database → Network restrictions**: restrict direct database access to the IPs that need it (Atls itself only uses the HTTPS API).
- [ ] **Advisors → Security Advisor**: no errors. All Atls tables have RLS enabled; `device_tokens` and `rate_limits` intentionally have no client policies.
- [ ] **Advisors → Performance Advisor**: review.
- [ ] Enable MFA on your Supabase account; add a second organization owner.
- [ ] Backups: daily backups are included on paid plans; enable Point-in-Time Recovery if the database will grow beyond a few GB.
- [ ] Rate-limit windows prune themselves as they are used; scheduling `select public.prune_rate_limits();` daily (Database → Cron) is optional.
- [ ] **Authentication → Sessions**: consider a time-box (for example 7 days) and an inactivity timeout for dashboard sessions.
- [ ] Turn on two-factor authentication for every owner and admin account in Atls (Settings → Two-factor authentication).

## 5. Verify

```bash
# The anon role sees only published advisories, and nothing else:
curl "https://<ref>.supabase.co/rest/v1/advisories?select=id" -H "apikey: <publishable key>"
curl "https://<ref>.supabase.co/rest/v1/receipts?select=id" -H "apikey: <publishable key>"   # → permission denied
```

RLS is also proven in CI on every push: `supabase/tests/rls.test.ts` applies the same migrations to Postgres (PGlite) and checks that a user of one organization cannot read or write another's receipts, policies, devices, locks, exports or audit log, that auditors cannot change anything, and that clients cannot call server-only functions.

## Rollback

Migrations are forward-only. To undo a change, write a new migration that reverses it and `supabase db push` it. Restore from a backup (or PITR) for data problems. Receipts, published policy versions and the audit log are append-only by design; do not drop those triggers to "fix" data.
